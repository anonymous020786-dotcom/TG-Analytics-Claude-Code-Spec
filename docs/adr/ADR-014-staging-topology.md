# ADR-014 — Staging Topology and Secret Delivery

Status: Accepted (PHASE-11B, 2026-09-29). Host, domain, TLS and managed secret store: OD-016.

## Context

PHASE-11B requires an isolated minimal staging environment with private datastores and secrets from a secret store, running the vertical slice on a small allow-listed set of public entities. DEPLOYMENT.md prescribes Cloudflare → Nginx → Docker, with PostgreSQL and Redis never publicly exposed. CLAUDE.md requires staging verification before production changes. The concrete host is not yet chosen (OD-016).

## Decision

- **One host-agnostic compose file** (`docker-compose.staging.yml`, project `tga-staging`). It runs on any Docker host, so it can be verified locally before OD-016 is resolved.
- **Network segmentation:**
  - `data` (internal): PostgreSQL, Redis, API, workers, migration job; no internet, no published ports;
  - `app` (internal): proxy, web, API;
  - `egress`: only the three Telegram-facing workers;
  - `edge`: only the proxy.
- **Single entry point:** unprivileged Nginx (image pinned by digest). It sets security headers, `noindex` and `robots.txt: Disallow: /`, propagates request IDs, writes JSON access logs, applies per-IP rate limits, sets upstream timeouts and caps body size. It binds to localhost by default; TLS terminates in front of it (Cloudflare or the host).
- **Secrets as Docker secrets files** mounted at `/run/secrets`:
  - apps read them via `*_FILE` (ADR-009), and PostgreSQL via `POSTGRES_PASSWORD_FILE`;
  - they're generated by `scripts/staging/init-secrets.mjs` into a git-ignored directory;
  - `APP_ENV=staging` rejects placeholder secrets.

  A managed secret store can replace the files without code changes.
- **Hardening:** app containers are read-only, drop all capabilities, set `no-new-privileges` and run as non-root.
- **Migrations** run as a one-shot `migrate` job that must succeed before the API and workers start.
- **Data scope:** `DISCOVERY_ALLOWLIST` restricts staging collection to a small allow-list (default `telegram,durov,bottalk`).
- **Images:**
  - one generic `worker` target (`WORKER` build argument) that assembles production `node_modules` plus built `dist/` only;
  - BuildKit cache mounts for the pnpm store and metadata, so supply-chain checks run once per build instead of per stage.

## Consequences

- Staging is reproducible and verifiable anywhere. A remote deployment still needs the OD-016 decisions.
- File-based secrets rely on host filesystem permissions until a managed store is chosen.
- Image sizes (API and workers about 0.7 GB, migrate about 2.7 GB) are larger than necessary; to be slimmed in PHASE-29/35.
